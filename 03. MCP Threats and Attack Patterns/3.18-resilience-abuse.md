# 3.18 Resilience, Abuse, and Availability (`ABUS`)

[← Chapter 3 overview](<3. MCP Threats and Attack Patterns.md>) · [Test case format](test-case-format.md)

## Overview

Resilience tests cover **abuse at scale**: tool-call storms, concurrency limits, retry semantics on non-idempotent operations, and cost amplification via model loops.

## Why this category matters

Agentic hosts can hammer tools and upstream APIs. Missing limits causes financial abuse, lockouts, or data corruption from duplicate writes.

## Scope

Rate limits, concurrency caps, idempotency keys, circuit breakers, planner retry policy.

## When to prioritize

High for production agents with billing-sensitive upstreams or write-heavy tools.

## Related categories

[AGNT](3.09-agentic-workflow.md), [GW](3.16-gateway-egress.md), [TRNS](3.15-transport-channel.md)

## Common test chains

ABUS-02 + AGNT-05; ABUS-01 + GW-03.

## Threats and attack patterns

This category is where the published record is thinnest. The sources below support the impact (cost, repeated side effects, resource exhaustion). They do not include a named incident whose title is “MCP tool-call storm.” Reports should say that plainly and attach the evidence from the test, not a CVE number the test did not match.

### Unbounded calls are a cost and availability bug

OWASP API Security Top 10, API4:2023, says exploitation can be ordinary API requests, including many concurrent ones, and that the weakness is common because APIs do not limit client interactions. The impact statement:

> “Exploitation can lead to DoS due to resource starvation, but it can also lead to operational costs increase such as those related to the infrastructure due to higher CPU demand, increasing cloud storage needs, etc.”
>
> — OWASP, [API4:2023 Unrestricted Resource Consumption](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)

Their first scenario is a forgot-password API that calls an SMS provider priced per message. A script repeats the first call; the bill follows. Their prevention list includes execution timeouts, maximum memory, rate limits per client and per operation, and spend limits or billing alerts on third parties. MCP tool calls that send mail, create tickets, or invoke a metered model are the same shape. The MCP-specific observation in Snyk’s `postmark-mcp` alert is volume without a person: “Agent-driven automation may have sent large volumes of messages with no human-in-the-loop, compounding exposure” ([Snyk, 25 September 2025](https://snyk.io/blog/malicious-mcp-server-on-npm-postmark-mcp-harvests-emails/)). That sentence is about a malicious package’s blast radius. It is still the published description of an MCP send tool running unattended.

**Tests:** `MCPSTG-ABUS-01`, `MCPSTG-GW-03`, `MCPSTG-TRNS-03`. Record the limit (requests per user, concurrent calls, message bytes, third-party spend) and the response when it is exceeded. Absence of a limit is the finding.

### Retries repeat a side effect

`MCPSTG-ABUS-02` asks whether a client or agent retries a tool that charges a card, sends a message, or creates a record. This guide did not find an MCP CVE that documents a duplicated charge caused by a retry loop. Willison’s lethal-trifecta post notes a related limit of that model: stopping data theft does not stop tools that cause damage without exfiltrating anything ([16 June 2025](https://simonwillison.net/2025/jun/16/the-lethal-trifecta/)). A retry of a non-idempotent tool is that damage path. Invariant’s GitHub demonstration created a pull request as the closing action of a flow the user did not fully specify ([GitHub MCP Exploited](https://invariantlabs.ai/blog/mcp-github-vulnerability)). A client that replays that `tools/call` after a timeout would open a second pull request if the server treats each call as new work.

**Tests:** `MCPSTG-ABUS-02`, `MCPSTG-AGNT-05`. Evidence is two server-side effects from one user intent, or a documented idempotency key that made the second call a no-op. Do not describe a lab retry as a public incident.

### Authentication and exposure multiply a small flood

The unauthenticated HTTP and SSE services in [CVE-2026-40576](https://github.com/advisories/GHSA-j98m-w3xp-9f56), [CVE-2026-59971](https://osv.dev/vulnerability/CVE-2026-59971), and the `mcp-atlassian` HTTP advisories accept calls from anyone who can reach the port. Those advisories’ primary impact is data access and, for some, code execution. They also remove the identity key a rate limit would use. A limit that keys only on “the MCP session” is weak when creating a session requires no credential. **Tests:** `MCPSTG-ABUS-01` on the same build you use for `MCPSTG-AUTHN-01`.

### Sampling as a cost channel

[Sampling Abuse](3.08-context-memory.md#sampling-abuse) includes a server that calls `sampling/createMessage` in a loop and spends the user’s model quota. Rate-limit that call per server the same way you rate-limit tool calls.

**Tests:** `MCPSTG-ABUS-01`.

## Rate-limit starting points

Document starting points and tune them to the product: **100 tool calls / minute / user**, **10,000 tokens of arguments / hour**, burst `20`. Then measure p99 latency impact. These numbers are examples, not a universal control. Gateway enforcement of the limit is [MCPSTG-GW-03](3.16-gateway-egress.md#mcpstg-gw-03).

### MCPSTG-ABUS-01 — Test Tool-Call Storms and Concurrency Limits

<a id="mcpstg-abus-01"></a>

#### Summary

Agentic MCP hosts can invoke tools in **tight loops** or at **high concurrency** when a planner retries, misinterprets errors, or follows poisoned instructions. Without host-level and server-level limits, a single session can exhaust CPU, flood upstream APIs, inflate token cost, or trigger account lockouts. This test checks whether rate limits, concurrency caps, and backpressure exist **before** shared infrastructure is impacted.

#### Scenario

- **MCP host/client:** `<TEST_USER>` runs a lab agent host connected to `<AUTHORIZED_LAB_SERVER>`.
- **MCP server:** exposes `<TEST_TOOL_NAME>` that performs a cheap but measurable action (for example a read or synthetic HTTP call to a lab-only endpoint).
- **Trust boundary:** between **planner retry policy**, **host throttling**, and **server/gateway enforcement**.
- **Attacker position:** abusive automation, runaway agent loop, or prompt that encourages repeated tool use.
- **Potential impact:** availability degradation, financial abuse (API billing), upstream rate-limit bans.

#### Test Objectives

- Verify maximum **calls per minute** and **concurrent in-flight** tool calls are enforced.
- Verify the host surfaces throttling to the user/model without silent infinite retry.
- Verify logs and metrics expose storm patterns for detection.

#### Preconditions

- Authorized lab with a dedicated MCP server and synthetic tool only.
- Ability to run a bounded concurrency script (see **Example snippets**).
- Metrics or logs for tool-call count, latency, and throttle/deny events.

#### How to Test

##### 1. Manual Review

Review host and server documentation for documented rate limits, queue depth, and planner retry policies.

##### 2. Configuration Review

Inspect host MCP policy, gateway throttling, and server-side limits. Note whether limits apply per user, per server, or globally.

##### 3. Runtime Testing

1. Establish baseline latency with a single `tools/call`.
2. Run the bounded burst script below with `limit=5`, then `20`, then `50` (stop if lab policy says so).
3. Record HTTP/MCP error codes, queue times, and whether calls are dropped or delayed.

##### 4. Abuse Case Testing

Combine burst traffic with a prompt that asks the model to “keep trying until success” and observe whether the host stops the loop.

##### 5. Log and Detection Review

Confirm throttle/deny events include principal, tool name, limit name, and correlation ID.

#### Example snippets

Lab host configuration:

```json
{
  "mcpServers": {
    "<AUTHORIZED_LAB_SERVER>": {
      "command": "node",
      "args": ["<TEST_WORKSPACE>/servers/lab-server/index.js"]
    }
  }
}
```

Single tool call (baseline):

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": { "query": "baseline-lab-1" }
  }
}
```

Bounded concurrency burst (authorized lab only):

```python
import asyncio
import json

async def call_tool(send, n):
    req = {
        "jsonrpc": "2.0",
        "id": n,
        "method": "tools/call",
        "params": {
            "name": "<TEST_TOOL_NAME>",
            "arguments": {"query": f"lab-burst-{n}"},
        },
    }
    return await send(json.dumps(req))

async def burst(send, limit=20):
    return await asyncio.gather(*[call_tool(send, i) for i in range(limit)])
```

Example host policy shape:

```yaml
mcp:
  rateLimits:
    toolsCall:
      maxPerMinute: 30
      maxConcurrent: 5
  planner:
    maxRetriesPerTool: 2
```

#### Test Data / Example Payloads

Use synthetic tool arguments only. Do not aim burst scripts at production endpoints or shared lab infrastructure without explicit approval.

#### Expected Results

- **Secure:** excess calls receive `429`/policy deny or queued backpressure; planner stops after configured retries; SIEM can alert on threshold breaches.
- **Insecure:** unbounded parallel calls succeed; upstream errors cause uncontrolled retry storms; no throttle telemetry.
- **Evidence:** redacted log lines showing limit enforcement, script parameters used, before/after call counts.

#### Remediation

- Enforce **per-principal** and **per-tool** rate limits on the host and gateway.
- Cap planner retries and require exponential backoff with jitter.
- Add circuit breakers when error rates spike.
- Expose metrics: `mcp_tool_calls_total`, `mcp_tool_throttled_total`.

#### Tools

Load generators (bounded), MCP client libraries, structured log search, metrics dashboards.

- CWE-770: Allocation of Resources Without Limits or Throttling.

### MCPSTG-ABUS-02 — Test Retry Behavior for Idempotent versus Non-Idempotent Side Effects

<a id="mcpstg-abus-02"></a>

#### Summary

A timeout can occur after a mutating tool has committed its effect. Retrying without the deployment's required idempotency controls can create a second effect. This test separates request attempts from committed effects and verifies the declared retry, payload-binding, and deduplication contract. A single marker file or unchanged final-content hash does not prove that only one execution committed.

#### Scenario

- **MCP host/client:** a reviewed lab client using bounded retries or explicit replay.
- **MCP server:** `<TEST_TOOL_NAME>_create_record` creates one uniquely identified synthetic record per committed operation inside `<TEST_WORKSPACE>/sandbox/`.
- **Observable effect:** count the committed records independently of request logs and the idempotency cache. An append-only effect ledger is suitable if each entry is itself the synthetic effect or reliably records the actual commit.
- **Trust boundary:** client retry policy → tool authorization → deduplication state → committed effect.
- **Potential impact:** repeated writes after uncertain outcomes, lost deduplication state, or concurrent retries.

#### Test Objectives

- Verify retries of the same authorized operation do not commit additional effects where the deployment promises deduplication.
- Verify the application key is bound to the documented principal, tool, and normalized business input.
- Distinguish new authorized operations, request attempts, duplicate handling, and committed effects.

#### Preconditions

- Written lab scope, synthetic records only, a sandbox, and a bounded attempt/concurrency budget.
- A tool whose schema explicitly supports an application idempotency key and whose contract defines key scope, payload binding, retention, and duplicate/in-progress handling. If unsupported, assess the documented no-blind-retry policy separately; do not assume every MCP tool implements this field.
- Independent committed-effect counts and, where supported, stable operation IDs. Final file counts, deduplication flags, and request logs alone are insufficient.
- A fault-injection mechanism that can suppress a response **after** a confirmed commit, without changing the request's business input.
- For concurrency checks, support for two controlled simultaneous calls and a way to observe their final outcomes.
- Record the MCP revision, transport, tool/client versions, authorization policy, and retry limit. These prerequisites describe a tester-provided lab, not a server bundled with the guide.

#### How to Test

##### 1. Manual Review

Document which operations are safe to repeat and which require deduplication or additional approval. Identify how the client resolves an uncertain outcome. Review [State, Retries, and Concurrency](<../04. Secure MCP Development.md#state-retries-and-concurrency>) for the guide's key-binding and changed-payload guidance.

##### 2. Configuration Review

Record the actual retry settings, approval rules, key scope, and deduplication retention window. Keep all replays within that window. Verify that the fixture's commit observable distinguishes two identical writes; an overwrite-only `marker.txt` fixture cannot do so.

##### 3. Runtime Testing

Use a fresh fixture or isolate records by case. Check the committed-effect count before and after each step.

1. **Valid baseline:** submit authorized payload A with key K1. Require one committed effect and capture its operation ID if available.
2. **Same-key retry:** send a new JSON-RPC request ID with the same principal, tool, K1, and normalized payload A. Require one total committed effect. Compare the operation identity or the documented duplicate/in-progress outcome. The application key, not the JSON-RPC ID, identifies the repeated operation.
3. **Lost response:** start a fresh case. Confirm the first K1/A request committed one effect, then suppress its response before the client receives it. Observe the client timeout/connection loss and retry K1/A with a distinct request ID. Require one total committed effect. A generic `503` or timeout without evidence of commit does not exercise this failure point.
4. **Changed payload:** in a fresh case, commit K1/A, then submit K1 with payload B. Under the documented changed-input rejection contract, require rejection and no additional effect. A cached success that silently ignores B does not establish that contract.
5. **Authorized fresh-key control:** submit a separately authorized operation with K2. Require exactly one additional effect. A new key is a new operation identity; deny or prompt only if the deployment's authorization policy requires it. Do not use a new key to retry the same uncertain operation.
6. Verify the actual client respects its configured retry limit where applicable. Manual replay proves the tool's observed behavior, not the planner's retry policy. Stop when the assessment's attempt budget is reached.

##### 4. Abuse Case Testing

Where supported, start a fresh case and submit two authorized K1/A requests concurrently, with distinct request IDs. Resolve any documented in-progress result through the supported outcome-query path. Require one final committed effect; do not assume that two responses or two request log entries mean two commits.

Validate the oracle against synthetic controls that ignore keys, lose deduplication state after commit, accept changed payloads, or race between checking a key and committing. Use deterministic synchronization where possible and no production targets. Record unsupported or unobservable cases as **not tested**, with the reason.

##### 5. Log and Detection Review

Correlate the case ID, authenticated principal, tool, request IDs, application key alias, normalized payload digest, commit/operation IDs, and final outcomes. Count request attempts separately from committed effects. A `deduped=true` message is supporting telemetry, not the deciding observable.

#### Example snippets

This example targets MCP revision `2026-07-28`. Replace the tool name and arguments with the advertised lab schema; use the required initialization and transport state for older revisions. `idempotencyKey` is a tool-specific argument in this fixture, not a universal MCP field. Every variant retains the revision metadata.

```json
{
  "jsonrpc": "2.0",
  "id": 10,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>_create_record",
    "arguments": {
      "value": "lab-A",
      "idempotencyKey": "lab-run-1"
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

| Case | Request ID | Application key | Business input | Expected committed effects |
| --- | --- | --- | --- | --- |
| Initial operation | `10` | `lab-run-1` | `lab-A` | One |
| Same-operation retry | `11` | `lab-run-1` | `lab-A` | Still one |
| Changed-input check | `12` | `lab-run-1` | `lab-B` | Still one; reject under the stated contract |
| Separately authorized new operation | `13` | `lab-run-2` | `lab-A` | Two total |

For the lost-response and concurrency cases, reset the fixture and reuse this business-input/key relationship with distinct request IDs. The fixture should produce a new record or operation ID for each actual commit, so duplicate execution remains visible even when the values are identical.

#### Test Data / Example Payloads

Use synthetic values and sandbox records only. For example, a local database's effect table can hold one uniquely identified record per committed create operation, while separate attempt logs and deduplication state track requests and keys. Count the effect records through an independent query; do not count the idempotency-cache entries as effects.

#### Expected Results

- **Secure:** an initial authorized operation commits once; same-key/same-input retries and supported concurrent requests produce one final effect within the documented retention window; changed input is handled according to the stated contract.
- **New operation:** an authorized new key commits one additional effect. Approval or denial follows the deployment's policy, not the mere fact that the key changed.
- **Insecure:** the same operation commits more than once after replay or a lost response, a race produces duplicate effects, or changed input violates the declared key-binding contract.
- **Inconclusive:** no independently observable commit count, unknown fault timing, unresolved in-progress outcomes, or an expired retention window. Do not infer a pass from a single marker or stable filesystem hash.
- **Evidence:** before/after committed-effect counts, operation IDs, request-attempt counts, payload digests, response/error observations, fault position, and the tested retry/retention configuration.

#### Cleanup

Save redacted evidence, remove synthetic records and key state, restore fault-injection and client settings, and stop lab services. Confirm that no fixture files, processes, or test credentials remain; record cleanup failures.

#### Remediation

- Disable blind retries of non-repeatable operations unless the deployment has a supported deduplication or outcome-query mechanism.
- Bind application keys to the authorized principal, tool, and normalized business input; reject changed input under a key where that is the contract.
- Coordinate committed effects and durable deduplication state, including concurrent requests, and retain operation identity/results for the promised retry window.
- Enforce retry bounds and reconcile uncertain outcomes rather than assuming timeout or cancellation rolled back an effect.

#### Tools

A reviewed MCP client, independent sandbox-record queries, redacted log correlation, and a lab-only response-loss/concurrency fixture. No general testing framework or third-party server installation is required by this procedure.
