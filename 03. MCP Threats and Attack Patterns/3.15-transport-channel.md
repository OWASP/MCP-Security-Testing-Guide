# 3.15 Transport and Channel Security (`TRNS`)

[← Chapter 3 overview](<3. MCP Threats and Attack Patterns.md>) · [Test case format](test-case-format.md)

## Overview

Transport tests examine **how MCP messages move**: TLS configuration, certificate validation, authentication binding to the channel, message size limits, and timeouts under load.

## Why this category matters

Remote MCP over HTTP introduces classic channel threats—MITM, credential theft, and DoS—on top of tool-level risks.

## Scope

TLS versions/ciphers, cert pinning, mTLS, session binding, max payload sizes, idle and read timeouts.

## When to prioritize

Mandatory for **remote** MCP; lower for pure stdio local-only deployments.

## Related categories

[AUTHN](3.03-identity-authentication.md), [GW](3.16-gateway-egress.md), [ABUS](3.18-resilience-abuse.md)

## Common test chains

TRNS-01 + AUTHN-02; TRNS-03 + ABUS-01 (storms/timeouts).

## Threats and attack patterns

Transport findings in the published record are command execution through an OAuth URL, missing Host checks on HTTP MCP, and servers that accepted sessions on all interfaces. Message-size limits are specified as a denial-of-service control in the tests below; this section does not cite a named “oversized MCP frame” CVE, because the sources reviewed here did not publish one.

### `authorization_endpoint` became a command

[CVE-2025-6514](https://www.cve.org/CVERecord?id=CVE-2025-6514), published 9 July 2025, also [GHSA-6xpm-ggf7-wc3p](https://github.com/advisories/ghsa-6xpm-ggf7-wc3p):

> “mcp-remote is exposed to OS command injection when connecting to untrusted MCP servers due to crafted input from the authorization_endpoint response URL.”
>
> — CVE-2025-6514

Affected versions are 0.0.5 through 0.1.15. The fixed version named by the advisory and by JFrog is 0.1.16. CWE-78. CVSS 3.1 base score 9.6, vector `CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H` (user interaction required, scope changed). JFrog’s [write-up](https://jfrog.com/blog/2025-6514-critical-mcp-remote-rce-vulnerability/) says the client asks the MCP server for OAuth metadata and then opens the returned `authorization_endpoint`. Their stated mitigations are to upgrade and to connect only to trusted MCP servers over HTTPS.

The MCP security best-practices document generalizes that bug. Clients must allow only `http` and `https` authorization URLs, must reject other schemes, and must not open URLs by calling a shell. Plain `http` is limited to loopback for development; production authorization servers use `https`.

> “OAuth authorization URLs provided by malicious MCP servers can exploit client-side URL handling vulnerabilities, leading to Cross-Site Scripting (XSS) attacks and Remote Code Execution (RCE).”
>
> — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices), OAuth Authorization URL Validation (28 July 2026 docs)

**Tests:** `MCPSTG-TRNS-01`, `MCPSTG-TRNS-02`. Record the TLS validation result and the function that opens the URL. A client that checks the certificate and then passes the URL to a shell still matches CVE-2025-6514’s class.

### DNS rebinding against loopback HTTP

[GHSA-89vp-x53w-74fx](https://github.com/modelcontextprotocol/rust-sdk/security/advisories/GHSA-89vp-x53w-74fx), `rmcp` before 1.4.0:

The Streamable HTTP server transport did not validate `Host`. The advisory says a public website can use DNS rebinding to send requests to an MCP server on loopback or a private address, which violates the specification’s transport guidance. Impact they state: read resources and prompts, and invoke tools the victim’s server exposes, which can include file writes and shell tools. The fix defaults the host allowlist to `localhost`, `127.0.0.1`, and `::1`, and returns HTTP 403 otherwise. The advisory says `Origin` validation is a follow-up and is not required to block this particular rebinding path, because the browser does not forge `Host` toward the rebound server. Public deployments are told to set an explicit allowlist or to put a reverse proxy in front that rejects unexpected `Host` values. Binding to `0.0.0.0` without that proxy is called out as unsafe.

[CVE-2026-59971](https://osv.dev/vulnerability/CVE-2026-59971) is the same class in MySQL MCP Server before 0.4.2. The CVE text says the SSE transport was constructed without `security_settings` or DNS-rebinding protection, routes had no authentication, and the default bind was `0.0.0.0`. A direct network attacker can call `execute_sql`, or a browser can be rebinding-relayed to a locally bound service. CWE-306 and CWE-346. Fixed in 0.4.2. Stdio is not affected.

Microsoft’s UFO advisory [GHSA-vf4c-mf32-gf2h](https://github.com/microsoft/UFO/security/advisories/GHSA-vf4c-mf32-gf2h) describes `linux_mcp_server.py` bound to `localhost:8010` with no Host, Origin, or `Sec-Fetch-*` checks, and says a rebinding page can call `execute_command` when it has the API key. Tool schemas were available from `tools/list` before that key was presented.

**Tests:** `MCPSTG-TRNS-02`. A pass is an allowlist check on `Host` (and a documented decision on `Origin`), not merely a bind to loopback.

### Cleartext and unauthenticated HTTP as the documented remote mode

[CVE-2026-40576](https://github.com/advisories/GHSA-j98m-w3xp-9f56) says the documented way to run `excel-mcp-server` remotely is SSE or Streamable HTTP, the default host is `0.0.0.0`, and there is no authentication. [CVE-2026-27825](https://github.com/advisories/GHSA-xjgw-4wvw-rgm4) and [CVE-2026-27826](https://github.com/advisories/GHSA-7r34-79r5-rcc9) say `mcp-atlassian` HTTP transports before 0.17.0 did not require authentication. Pluto Security’s write-up says that mode defaulted to all interfaces ([MCPwnfluence](https://pluto.security/blog/mcpwnfluence-cve-2026-27825-critical/)).

The authorization specification tells HTTP implementations to use OAuth 2.1 and tells stdio implementations not to follow that HTTP authorization spec. The security best-practices document says local servers that need to be remote should prefer stdio, or if they use HTTP, require a token or use a restricted IPC socket. **Tests:** `MCPSTG-TRNS-01`, `MCPSTG-TRNS-02`.

### Size and timeout

OWASP API4:2023 says APIs that do not limit execution time, memory, upload size, or the number of operations in one request can be driven into resource exhaustion or unexpected cost ([Unrestricted Resource Consumption](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)). That is general API guidance, not an MCP incident. `MCPSTG-TRNS-03` applies it to MCP message size and request timeout. Pair it with [3.18](3.18-resilience-abuse.md). If a product has no documented limit, the finding is the missing limit, not a claim that a particular CVE was reproduced.

### Canonical attack patterns

The write-ups below moved here from the threats chapter. Each one names the abuse, a lab-safe example, the impact, red flags, and defensive checks. Published cases earlier in this section remain the sourced record. Use both when you choose tests.

### Localhost Exposure and DNS Rebinding

**Tests:** `MCPSTG-TRNS-02`, `MCPSTG-CONF-02`, `MCPSTG-CONF-05`.

A local MCP server feels private because it listens on `127.0.0.1`. Browsers do not treat that as a security boundary. DNS rebinding is the classic way through: a page the user opened uses a name the attacker controls, the name first resolves to the attacker’s host so the browser allows the script, then it resolves to `127.0.0.1`, and the script talks to the local server. If that server has no authentication and does not check `Origin` or `Host`, the page can call tools as if it were the desktop agent.

The official security guidance says local servers should prefer `stdio`, which only the parent client can speak, and that HTTP on the loopback interface needs an authorization token or a restricted IPC socket. It also names DNS rebinding as a realistic way to reach a sloppy local listener. ([Model Context Protocol](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices))

Several official SDKs shipped with that protection off by default for unauthenticated HTTP. The public advisories are the same bug in four languages:

| SDK | Advisory | Affected range | Fixed in |
| --- | --- | --- | --- |
| TypeScript `@modelcontextprotocol/sdk` | CVE-2025-66414 | before 1.24.0 | 1.24.0 |
| Python `mcp` | CVE-2025-66416 | before 1.23.0 | 1.23.0 |
| Go SDK | CVE-2026-34742 | before 1.4.0 | 1.4.0 |
| Java `io.modelcontextprotocol.sdk:mcp-core` | CVE-2026-35568 | before 1.0.0 | 1.0.0 |

The TypeScript and Python advisories do not apply to `stdio`. They apply when an HTTP or SSE server is bound locally without authentication and without the SDK’s host or origin checks. Custom transports that bypass the SDK’s default app setup can still turn the protection back off, so “we upgraded” is not the whole story. Confirm the fixed release in each advisory before you freeze a version floor. ([TypeScript SDK advisory](https://github.com/advisories/GHSA-w48q-cv73-mx4w)) ([Python SDK advisory](https://github.com/advisories/GHSA-9h52-p55h-vw2f)) ([Go SDK advisory](https://nvd.nist.gov/vuln/detail/CVE-2026-34742)) ([Java SDK advisory](https://nvd.nist.gov/vuln/detail/CVE-2026-35568))

#### Impact

* A malicious website invokes local tools: file reads, shell helpers, whatever that server exposed.
* The user approved nothing, because the call never passed through the MCP client’s consent UI.
* Developer machines become a target for ordinary web browsing.

#### Red flags

* HTTP MCP servers bound to all interfaces, or to localhost with no token.
* Missing `Origin` and `Host` checks on the message endpoint.
* SDK versions older than the floors above, including transitive ones inside a desktop app.
* “It is only localhost” used as the reason there is no auth.

#### Defensive guidance

* Prefer `stdio` for local servers.
* If you must use HTTP, require a token, validate `Origin` and `Host` against an allowlist, and bind to loopback on purpose.
* Turn on the SDK’s DNS-rebinding protection even when you build the HTTP stack yourself.
* Keep local servers off the corporate image unless they are on the approved list from [Shadow MCP Servers](3.14-enterprise-governance.md#shadow-mcp-servers).

### Hostile Server URLs and Install Commands

**Tests:** `MCPSTG-TRNS-02`, `MCPSTG-CONF-01`, `MCPSTG-SUPP-03`.

Connecting to an MCP server is supposed to be a handshake. In a few widely deployed clients it has been an execution boundary.

`mcp-remote` is a small proxy that lets stdio-only hosts talk to a remote HTTP server. Versions 0.0.5 through 0.1.15 could be driven into OS command execution by a malicious server during authorization. The server answered with a crafted `authorization_endpoint`, and the client’s handling of that URL became a shell command. JFrog reported it as CVE-2025-6514, CVSS 9.6, CWE-78, fixed in 0.1.16. The practical lesson outlived that one package: any client that opens a server-supplied URL, or shells out to start a server, has to assume the other end is hostile. ([JFrog](https://jfrog.com/blog/2025-6514-critical-mcp-remote-rce-vulnerability/)) ([GitHub Advisory Database](https://github.com/advisories/GHSA-6xpm-ggf7-wc3p))

The specification describes the same family without naming a CVE.

* A one-click install runs whatever command string is in the config, including a chained download or a read of `~/.ssh`.
* An authorization URL uses `javascript:` or `data:` and the client passes it to a browser API.
* The client opens URLs with `cmd.exe`, PowerShell, or a shell script, so metacharacters in the URL become extra commands.
* A local proxy that can spawn stdio servers will spawn an attacker-chosen command if a web bug in the client can present the proxy’s token.

#### Impact

* Full compromise of the developer machine at connect time, before any tool is called.
* Stolen SSH keys, cloud credentials, and source checkouts.
* A browser-side bug that escalates into a local process because a proxy was willing to spawn one.

#### Red flags

* Install snippets that pipe a remote script into a shell.
* Clients that open authorization URLs through a shell.
* Remote MCP endpoints accepted over cleartext HTTP, or from a domain nobody has reviewed.
* Proxy processes that spawn arbitrary stdio commands for any caller who holds a local token.

#### Defensive guidance

* Connect only to servers you meant to connect to, over HTTPS, on a pinned version.
* Show the full command and arguments before a local server starts, with no truncation, and run it in a sandbox.
* Allow only `http` and `https` authorization URLs, and allow `http` only for loopback in development. Open them with the platform’s URL API, never a shell.
* Treat an upgrade of `mcp-remote` and of every host that grew its own remote-connect feature as a security patch, then re-read the release notes. Another client can have the same shape of bug.

### mcp-remote, restated as an incident

[Hostile Server URLs and Install Commands](#hostile-server-urls-and-install-commands) already records CVE-2025-6514. The operational context from later summaries is why it belongs in a sample list and not only in a CVE table.

`mcp-remote` was the adapter that let stdio-only hosts — Claude Desktop, VS Code with Copilot, Cursor — talk to a remote HTTP server. UpGuard, citing Docker Security Research, puts the download count above 437,000 and notes that Cloudflare, Hugging Face, and Auth0 integration guides told developers to install it. Versions 0.0.5 through 0.1.15 trusted the `authorization_endpoint` a remote server returned and could turn that URL into a shell command. Fixed in 0.1.16. CVSS 9.6, CWE-78. ([JFrog](https://jfrog.com/blog/2025-6514-critical-mcp-remote-rce-vulnerability/)) ([UpGuard](https://www.upguard.com/blog/mcp-security-incidents))

The lesson that outlives the version range: the package a security review approved may be the server, while the code that runs on the laptop is the proxy named in someone else’s getting-started guide. Inventory adapters, not only servers.

## Separate OAuth clients per environment

A development token must not be accepted on the production route. Issue separate OAuth client IDs for development, stage, and production, and validate audience and tenant claims before the gateway forwards `tools/call`. The claim checks are in [3.3](3.03-identity-authentication.md#enterprise-identity-at-the-gateway).

### MCPSTG-TRNS-01 — Test TLS Configuration and Certificate Validation

<a id="mcpstg-trns-01"></a>

#### Summary

Remote MCP transports rely on TLS for confidentiality and integrity between **client** and **server**. Weak cipher suites, missing certificate validation, or mis-terminated TLS at an untrusted hop exposes tokens, tool arguments, and resource payloads. MCP deployments often sit behind reverse proxies; misconfiguration there becomes part of the MCP trust boundary.

#### Scenario

- **MCP host/client:** Connects to a remote MCP endpoint over HTTPS.
- **Infrastructure:** TLS terminates at a load balancer; backend may be plaintext on a private network.
- **Attacker position:** Network observer on untrusted Wi‑Fi path to public endpoint; or compromised proxy in a misconfigured enterprise path.
- **Potential impact:** Credential theft, session hijack, undetected tampering with tool definitions in transit.

#### Test Objectives

- Verify **TLS versions**, **cipher strength**, and **certificate chain validation** meet organizational baselines.
- Verify **SNI** and **hostname** validation align with the MCP server identity.
- Identify **insecure** patterns: cert pinning disabled globally, `insecureSkipVerify`-style flags, mixed content downgrades.

#### Preconditions

- Authorized test against **lab** MCP HTTPS endpoint (not customer production).
- Permission to run TLS assessment tooling from an approved scanner host.
- Access to proxy/load balancer configuration (redacted).

#### How to Test

##### 1. Manual Review

Read deployment docs for TLS termination points and which component validates client certificates (if mTLS is claimed).

##### 2. Configuration Review

Inspect server and proxy configs for deprecated protocols (TLS 1.0/1.1), weak DH parameters, and permissive trust stores shipping private roots without justification.

##### 3. Runtime Testing

1. Connect with a known-good client and capture negotiated TLS version/cipher via approved SSL scanning (lab scope).
2. Attempt **hostname mismatch** using a valid certificate for a different name—expect **failure**.
3. If mTLS is required, attempt connection **without** client cert—expect **failure**.

##### 4. Abuse Case Testing

- Certificate expiry near-miss: deploy short-lived lab cert and verify renewal alarms (process test).
- Revocation behavior: document whether stapled OCSP/CRL checks are enforced (design documentation acceptable if live revocation tests are disallowed).

##### 5. Log and Detection Review

**Detection:** TLS handshake failures, cert validation errors, and proxy anomalies should be logged with client identity where available.

#### Test Data / Example Payloads

Use scanner profiles restricted to `<AUTHORIZED_LAB_SERVER>` hostnames only.

#### Expected Results

- **Secure:** TLS 1.2+ with modern ciphers; strict hostname validation; no silent bypass flags in production paths.
- **Insecure:** handshake succeeds with obsolete ciphers; tool traffic readable on the wire in lab capture.
- **Evidence:** redacted scan summary, config snippets with secrets removed.

#### Remediation

- Enforce TLS 1.2+ and modern cipher suites at the edge; automate cert lifecycle.
- Avoid `insecureSkipVerify` in production builds; isolate debug builds.
- Document trust store ownership and change control.

#### Tools

- Approved TLS scanners, `openssl s_client` in lab, cloud provider TLS policy dashboards.

#### References

- OWASP Web Security Testing Guide (structure inspiration only).
- OWASP ASVS 5.0.0: V12 Secure Communication (TLS-related verification).
- CWE-295: Improper Certificate Validation
- CWE-326: Inadequate Encryption Strength

#### Mapping

- [OWASP ASVS 5.0.0](https://owasp.org/www-project-application-security-verification-standard/): [v5.0.0-12.1.1](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x21-V12-Secure-Communication.md) (TLS versions), [v5.0.0-12.1.2](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x21-V12-Secure-Communication.md) (cipher suites), [v5.0.0-12.3.2](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x21-V12-Secure-Communication.md) (TLS server certificate validation), [v5.0.0-12.1.3](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x21-V12-Secure-Communication.md) (mTLS client certificate validation where required)

### MCPSTG-TRNS-02 — Test Transport Authentication Binding

<a id="mcpstg-trns-02"></a>

#### Summary

**Transport authentication binding** asks whether MCP sessions are tied to the **intended identity, tenant, and origin** for the transport in use. Failures include accepting bearer tokens on the wrong virtual host, missing **origin** checks on browser-originated traffic, confused deputy behavior behind shared reverse proxies, and stdio servers that treat **any local process** on the pipe as trusted.

#### Scenario

- **Remote transport:** MCP over HTTPS where the same load balancer serves multiple tenants or environments.
- **Local transport:** stdio MCP server launched by a host; a second local process attempts to attach if file descriptors leak or sockets are world-accessible (misconfiguration).
- **Attacker position:** Network client presenting a stolen token to the wrong MCP base URL; or local malware exploiting permissive IPC.
- **Potential impact:** Cross-tenant tool execution, session fixation, or silent proxy mis-routing of MCP JSON-RPC.

#### Test Objectives

- Verify tokens and session handles are **audience-bound** (hostname, path prefix, tenant id) where applicable.
- Verify browser-facing deployments use appropriate **origin**, **CORS**, and **cookie** flags consistent with your threat model—not “wide open because it is internal.”
- Verify stdio/socket transports cannot be reached from unintended OS principals.

#### Preconditions

- Lab URLs for at least two logical MCP “tenants” or path prefixes on the same infrastructure (if that matches production topology).
- Two test tokens (or mTLS identities) scoped to different audiences, synthetic only.
- Permission to inspect proxy routing rules (redacted).

#### How to Test

##### 1. Manual Review

Document the chain: **who authenticates whom** (client→server, server→upstream). Identify whether the MCP endpoint URL is part of the cryptographic or logical binding for tokens.

##### 2. Configuration Review

- For HTTPS: check virtual host routing, default backends, and whether a missing `Host` header falls through to a sensitive MCP instance.
- For cookies (if used): `Secure`, `HttpOnly`, `SameSite`, path scope.
- For stdio: process launch arguments, file descriptor inheritance, and socket filesystem permissions.

##### 3. Runtime Testing

1. Obtain a **valid** lab token scoped to tenant A.
2. Present it to the MCP endpoint that should only serve tenant B (same LB, different path or host)—expect **reject**.
3. Repeat with correct endpoint—expect **accept**.

##### 4. Abuse Case Testing

- Replay captured MCP messages with a rotated nonce or session id if your stack uses such fields—expect strict failure modes, not partial execution.
- If applicable, attempt cross-origin browser calls from an unauthorized lab origin—expect deny.

##### 5. Log and Detection Review

**Detection:** authentication failures should log **reason codes** (audience mismatch, unknown client, clock skew) without printing secrets.

#### Test Data / Example Payloads

Use synthetic hostnames only, for example `mcp-lab-a.<AUTHORIZED_LAB_SERVER>` vs `mcp-lab-b.<AUTHORIZED_LAB_SERVER>`.

#### Expected Results

- **Secure:** wrong audience or origin cannot initialize a session or call tools; stdio server only parent process can communicate.
- **Insecure:** token works on unintended tenant route; world-readable Unix socket accepts connections.
- **Evidence:** redacted proxy rules, auth error logs, minimal PCAP excerpts in lab.

#### Remediation

- Bind access tokens to **issuer, audience, and MCP resource identifier**; reject default-backend fallthrough.
- Harden local transports: least-privilege OS users, restricted socket paths, explicit parent–child process relationship checks where feasible.
- Prefer mTLS or signed connection bootstrap for high-risk remote MCP.

#### Tools

TLS proxies, JWT debugging utilities (lab tokens only), web browser devtools for origin checks, `lsof` / permission audits for local sockets.

#### References

- OWASP ASVS 5.0.0: 10.3.1 (OAuth access-token audience); 12.1.3 (mTLS client certificate validation).
- OWASP API Security Top 10: API2 Authentication Failures.
- CWE-287: Improper Authentication
- CWE-306: Missing Authentication for Critical Function

#### Mapping

- [OWASP API Security Top 10](https://owasp.org/API-Security/): [API2:2023 Broken Authentication](https://owasp.org/API-Security/editions/2023/en/0xa2-broken-authentication/)
- [OWASP ASVS 5.0.0](https://owasp.org/www-project-application-security-verification-standard/): [v5.0.0-10.3.1](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x19-V10-OAuth-and-OIDC.md) (OAuth access-token audience validation), [v5.0.0-12.1.3](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x21-V12-Secure-Communication.md) (mTLS client certificate validation where used); these mappings do not cover every origin, tenant-isolation, or local-transport check above

### MCPSTG-TRNS-03 — Test Message Size Limits and Timeouts Under Load

<a id="mcpstg-trns-03"></a>

#### Summary

MCP sessions can carry **large tool results**, **big resource reads**, or **verbose logging** embedded in JSON-RPC payloads. Without **maximum message size**, **stream backpressure**, and **timeouts**, servers become fragile under abuse or accidental “runaway” model outputs. This is availability and sometimes confidentiality (crash-induced error pages, partial writes).

#### Scenario

- **Host + model** return a multi-megabyte tool payload (logs, file dumps) in a single response.
- **Attacker or buggy tool** sends an oversized argument blob or floods parallel `tools/call` requests.
- **Potential impact:** process OOM, thread pool exhaustion, cascading failures in shared gateways, inflated egress costs.

#### Test Objectives

- Verify hard and soft limits on **request and response** sizes at client, server, and gateway.
- Verify **timeouts** for idle streams, slow clients, and hung tool executions.
- Verify **graceful** rejection (typed error) rather than opaque crashes.

#### Preconditions

- Lab-only load driver permitted in scope (low concurrency first).
- Monitoring for CPU, memory, and open connections on MCP server and gateway.

#### How to Test

##### 1. Manual Review

Read limits documentation: defaults, overrides, and whether limits differ for stdio vs HTTP.

##### 2. Configuration Review

Inspect gateway `max_body_size`, server read buffers, client timeouts, and tool-specific caps (for example “max bytes read from file tool”).

##### 3. Runtime Testing

1. Send a **just-below-limit** synthetic payload and confirm success.
2. Send a **just-above-limit** payload—expect HTTP 413 or protocol-specific error without server crash.
3. Open a connection and **stall** sending mid-message beyond idle timeout—expect disconnect and cleanup.

##### 4. Abuse Case Testing

- Bounded parallel tool calls (N small calls), stepping N upward until latency budgets break—stop before harming shared infrastructure.
- Very long-lived SSE/WebSocket streams: verify heartbeat and max duration.

##### 5. Log and Detection Review

**Detection:** rate-limit hits, timeout reasons, and payload size rejections should appear in metrics with MCP method names.

#### Test Data / Example Payloads

Generate in-lab random base64 blobs of known sizes (for example 512 KiB, 2 MiB, 8 MiB) **without** compressing secrets into them.

#### Expected Results

- **Secure:** limits enforced with clear errors; no sustained memory growth; connections closed cleanly.
- **Insecure:** worker crash, gateway 502s to unrelated tenants, or silent truncation that corrupts JSON framing.
- **Evidence:** metric charts, redacted error payloads, versioned config snippets.

#### Remediation

- Enforce layered limits: edge, MCP server, tool runtime.
- Stream large artifacts to object storage with signed URLs instead of inline MCP messages where appropriate.
- Add circuit breakers and per-principal concurrency caps (`MCPSTG-ABUS-01`).

#### Tools

Load generators in lab, observability stacks, `curl`/`h2load` with size-controlled bodies where permitted.

#### References

- OWASP ASVS 5.0.0: 15.2.2 (availability defenses); 13.1.3 (resource-management and timeout documentation).
- CWE-400: Uncontrolled Resource Consumption
- CWE-770: Allocation of Resources Without Limits or Throttling
