# 3.2 Configuration and Deployment Management (`CONF`)

[← Chapter 3 overview](<3. MCP Threats and Attack Patterns.md>) · [Test case format](test-case-format.md)

## Overview

MCP servers often run as **local processes** with filesystem access, environment variables, and transport bindings chosen by the host. Misconfiguration can expose servers to the network, leak secrets in debug output, or grant tools overly broad workspace access.

## Why this category matters

Many MCP incidents are deployment mistakes: debug flags left on, servers listening beyond localhost, permissive file ACLs, or mixed prod/lab config on the same host.

## Scope

Server startup flags, host integration config, config file locations, local process isolation, transport mode (stdio/streamable HTTP), debug/verbose error settings, workspace and file permissions.

## When to prioritize

High for **desktop hosts** and **self-hosted servers**. Pair with SECR and TRNS when remote exposure exists.

## Related categories

[TRNS](3.15-transport-channel.md), [SECR](3.17-secrets-credentials.md), [AUTHN](3.03-identity-authentication.md)

## Common test chains

CONF-02 (local exposure) → AUTHN-01 (missing authn on reachable server); CONF-03 (verbose errors) → RSRC-04 (secret leakage).

## Threats and attack patterns

Published deployment failures in this category are mostly “the server listened too widely, and then a second bug became remotely reachable.” Quotations below are from the linked advisory or from the MCP project’s own security document.

### All-interface bind plus no authentication

The GitHub Advisory Database entry for [CVE-2026-40576](https://github.com/advisories/GHSA-j98m-w3xp-9f56) (`excel-mcp-server` through 0.1.7) states that SSE and Streamable HTTP are the documented remote transports, that FastMCP’s default host is `0.0.0.0` via `FASTMCP_HOST`, and that those transports ship with no authentication. The advisory says anyone who followed the README and ran `uvx excel-mcp-server streamable-http` without setting `FASTMCP_HOST` exposed the server to the LAN, and that every tool handler then called `get_excel_path()` with a caller-supplied path.

[CVE-2026-59971](https://osv.dev/vulnerability/CVE-2026-59971) (MySQL MCP Server, fixed in 0.4.2; also listed by [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-59971)) describes the same deployment shape for a different product. The CVE text says that `MCP_TRANSPORT=sse` builds the SSE transport without DNS-rebinding protection, that `/`, `/sse`, and `/messages/` have no authentication, and that the service binds to `0.0.0.0` by default. The default stdio transport is not affected. Impact stated in the CVE: unauthenticated disclosure and modification of the configured database; with the MySQL `FILE` privilege, the same access can read or write server files.

`mcp-atlassian` before 0.17.0 is the third published example. [CVE-2026-27825](https://github.com/advisories/GHSA-xjgw-4wvw-rgm4) and [CVE-2026-27826](https://github.com/advisories/GHSA-7r34-79r5-rcc9) (both published 24 February 2026) say the HTTP transports carried no authentication. Pluto Security’s [MCPwnfluence](https://pluto.security/blog/mcpwnfluence-cve-2026-27825-critical/) write-up says `--transport streamable-http` defaulted to `0.0.0.0`.

**Tests:** `MCPSTG-CONF-02`, `MCPSTG-CONF-05`, then [3.3](3.03-identity-authentication.md) for the missing-auth check and [3.15](3.15-transport-channel.md) for Host-header and DNS-rebinding checks.

### Localhost is still reachable if Host is not checked

[GHSA-89vp-x53w-74fx](https://github.com/modelcontextprotocol/rust-sdk/security/advisories/GHSA-89vp-x53w-74fx) (rmcp, the official Rust SDK, fixed in 1.4.0) says the Streamable HTTP server transport did not validate the `Host` header before that release. A public site could use DNS rebinding to send requests to an MCP server on loopback or a private-network address. The advisory says the practical impact “can extend to arbitrary code execution” when the victim’s server exposes filesystem, shell, or similar tools. The fix defaults `allowed_hosts` to `localhost`, `127.0.0.1`, and `::1`.

The MySQL MCP CVE above names the same class (CWE-346, origin validation) for a server that also bound all interfaces, so both direct exposure and rebinding are in the advisory text.

**Tests:** `MCPSTG-CONF-02`, `MCPSTG-CONF-05`. Do not treat “bound to 127.0.0.1” as sufficient without a Host or Origin allowlist, or a reverse proxy that enforces one.

### One-click install runs an unreviewed command

The MCP security best-practices document lists three local-server conditions: a malicious startup command in client configuration, a malicious payload inside the server, and access to an insecure local server via DNS rebinding. It also states the client must show the exact command, without truncation, and identify it as code execution on the user’s system.

> “Warn that MCP servers run with the same privileges as the client.”
>
> — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices), Model Context Protocol (28 July 2026 docs)

Snyk’s `postmark-mcp` note is the registry-side version of the same deployment fact: after npm removed the package on 25 September 2025, “installed copies keep running until explicitly uninstalled.” See [3.13](3.13-supply-chain.md).

**Tests:** `MCPSTG-CONF-01`, `MCPSTG-CONF-04`.

### Error detail is itself a disclosure channel

The same MCP security document, in its SSRF section, lists this risk of a client that fetches attacker-influenced OAuth URLs:

> “Internal network reconnaissance: Error messages reveal information about internal network topology and services.”
>
> — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices), Server-Side Request Forgery

This guide did not find a separate CVE whose sole impact was “MCP debug mode.” The published guidance still treats verbose errors as a way internal addresses and service names leave the server. [CVE-2026-27826](https://github.com/advisories/GHSA-7r34-79r5-rcc9) separately says an unauthenticated header SSRF in `mcp-atlassian` enables internal network reconnaissance and can inject attacker-controlled content into LLM tool results.

**Tests:** `MCPSTG-CONF-03`.

### Related patterns for local servers

Three patterns in other sections are configuration findings when you inventory how a server is installed and where it listens:

- [Shadow MCP Servers](3.14-enterprise-governance.md#shadow-mcp-servers) — unmanaged servers on developer machines and in shared config.
- [Localhost Exposure and DNS Rebinding](3.15-transport-channel.md#localhost-exposure-and-dns-rebinding) — a browser page reaching an unauthenticated loopback listener.
- [Hostile Server URLs and Install Commands](3.15-transport-channel.md#hostile-server-urls-and-install-commands) — a connect or install step that runs a server-supplied command.

**Tests:** `MCPSTG-CONF-01`, `MCPSTG-CONF-02`, `MCPSTG-CONF-05`.

### Host configuration files

A host config is an execution policy written as JSON. It names the program the host will start, the arguments, the environment, and sometimes a remote URL. Teams copy these files between machines and commit them into repositories. That is how a sandbox config ends up pointing at production credentials on another laptop.

Real host files mostly record a command, an argument list, an environment map, or a remote URL. A path on the command line is a hint to an honest server. A server that ignores it can still read whatever the operating system lets that process read. The fence is the host’s sandbox, a container mount, or file permissions, covered in [Local servers are processes](#local-servers-are-processes).

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/alice"]
    },
    "terminal": {
      "command": "python",
      "args": ["mcp_shell_server.py"],
      "autoApprove": ["run_command"]
    }
  }
}
```

This entry is risky because the filesystem server is rooted at the home directory, the terminal server can execute commands, `run_command` is auto-approved, and `npx -y` skips the install prompt and resolves the package when the host starts. Tomorrow’s release can land without a config diff. Naming `package@1.2.3` pins only that package. Launchers such as `npx` and `uvx` typically resolve dependencies again at install time. An image pinned by digest freezes the whole tree. Pin the release that was reviewed. Provenance and registry checks are in [3.13](3.13-supply-chain.md).

A block that adds `permissions`, `allowedPaths`, and `approval.requireFor` is a picture of what a host policy engine should decide. It is not JSON that Claude Desktop, Cursor, or VS Code will enforce. A config that matches what these hosts actually store looks like this:

```json
{
  "mcpServers": {
    "project-files": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem@1.2.3", "/Users/alice/work/demo-project"],
      "env": {
        "EXAMPLE_TOKEN": "prefer-a-secret-store-over-this-file"
      }
    }
  }
}
```

The `1.2.3` above is a placeholder. Tokens in `env` or in HTTP `headers` sit in a well-known file on disk. Prefer the operating system secret store when the host can read from it. ([Cursor](https://cursor.com/docs/mcp))

| Control | What to do |
| --- | --- |
| Default deny | New servers and tools start disabled or require explicit approval. |
| Least privilege paths | Limit filesystem servers to the project directory. |
| Separate read and write | Use a read-only server when the job is reading. Require a higher approval for write or delete. |
| No broad auto-approval | Do not auto-approve shell, network, credential, database write, email, payment, ticket update, or deployment tools. Approval UX is in [3.4](3.04-authorization-permission.md#tool-permission-ux). |
| Config integrity | Protect the file with user-only permissions and alert on change. Detection queries are in [3.12](3.12-logging-detection.md#mcp-configuration-change-detection). |
| Environment separation | Use different configs for personal, development, staging, and production. |

Record each row as Pass, Partial, Fail, Accepted Risk, or N/A. Status values are in [Appendix C](<../09. Appendix C - Security Review.md>).

| Check | What to verify | Why it matters | Evidence to collect | Good examples | Common gaps |
| --- | --- | --- | --- | --- | --- |
| Installed servers are visible | The user can see every enabled server, including command, arguments, version, and source. | A hidden server cannot be reviewed. | UI screenshot. | Server list shows the full launch command. | A server runs with no entry in the UI. |
| Config files are protected | MCP config is not writable by untrusted projects or other users. | A malicious repo may try to alter local MCP config. | File permissions, config location. | User-only writable config. | A workspace file modifies global MCP config. |
| Server commands are reviewed | Launch commands are allowlisted and paths are narrow. | MCP config can become code execution. | Config review, command allowlist. | An approved binary with fixed args and a workspace path. | `npx some-random-package@latest` rooted at the home directory. |
| Env vars are minimized | The client does not pass the whole user environment to servers. | Prevents credential leakage. | Launch config. | One scoped token. | The shell environment is inherited. |
| Config changes are visible | Users and admins see schema, tool, or server changes before activation. | Detects tampering and drift. | Change log, notification. | “New server added by config change.” | Silent config mutation. |
| Managed policy is supported | A central allowlist and denylist exist. | User-only settings do not scale. | Admin policy docs. | Central allowlist. | Every developer configures servers by hand. |
| Emergency disable exists | A user or admin can disable all MCP servers without editing files. | Containment has to be fast. | UI or device-management control. | “Disable all MCP servers.” | Only per-server config edits. |

Minimum acceptance: MCP config cannot silently run an unreviewed command or leak a broad environment.

### Where host configs live

“Check the MCP config” only helps if the review names every file the host will read, including one a repository brought with it. Paths move between versions. Confirm them against the vendor page for the build you run.

| Host | Workspace file | User-level file |
| --- | --- | --- |
| VS Code | `.vscode/mcp.json` (`servers`) and portable `.mcp.json` (`mcpServers`) | User profile `mcp.json`, and `~/.copilot/mcp-config.json` for the portable user file |
| Cursor | `.cursor/mcp.json` | `~/.cursor/mcp.json` |
| Claude Desktop | — | macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`. Windows: `%APPDATA%\Claude\claude_desktop_config.json`. Linux: `~/.config/Claude/claude_desktop_config.json` |
| Windsurf | — | `~/.codeium/windsurf/mcp_config.json` |

VS Code’s configuration reference maps the Claude, Copilot, Cursor, and Windsurf paths in one table. ([Visual Studio Code](https://code.visualstudio.com/docs/agents/reference/mcp-configuration)) Cursor documents the global file and the project file. ([Cursor](https://cursor.com/docs/mcp)) VS Code can also import those other configs when `chat.mcp.discovery.enabled` is on. ([Visual Studio Code](https://code.visualstudio.com/docs/agent-customization/mcp-servers)) Discovery enables a server, headers included, that someone reviewed in a different app months ago.

A cloned repo can contain an installer. `.cursor/mcp.json`, `.vscode/mcp.json`, and `.mcp.json` are ordinary project files. Anyone who can merge can add a `command`. That is the same class of change as a CI job or a `postinstall` script. VS Code’s add-server flow prefers the portable `.mcp.json` and still loads `.vscode/mcp.json`, so a review of one filename misses the other. [Workspace trust](3.04-authorization-permission.md#workspace-trust) should refuse to spawn a command that arrived with an untrusted folder. ([Visual Studio Code](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust))

The file is a secret store whether that was intended or not. `env` values and HTTP `headers` are how hosts pass tokens. The files live at predictable paths, get copied into dotfiles repos, and sync if the editor syncs settings. An internal package-registry URL in that file is sensitive even when the token is somewhere else. Machines that hold production credentials should keep MCP config out of unmanaged settings sync.

Fleet inventory is file collection. Endpoint tooling that already reads known paths can answer who is running which server, at which version, from which command. That list is the starting point when a local server or the SDK inside it is compromised: find the configs, block the destinations, rotate the tokens those files held, and push a pinned replacement.

* [ ] Every file the host will load is known, including workspace files and configs discovered from other apps.
* [ ] `.cursor/mcp.json`, `.vscode/mcp.json`, and `.mcp.json` are in code review, and `command`, `args`, `url`, and `headers` are treated as executable.
* [ ] Discovery of other hosts’ MCP configs is off unless someone owns the result.
* [ ] Settings sync and dotfile backup are excluded from machines that hold production tokens.
* [ ] Endpoint management can list these files across the fleet.

### Local servers are processes

When a host adds a local server, it starts a program. With stdio, the client spawns that program and talks to it on stdin and stdout. The SDK does not defend either side of that pipe. A malicious server already has code execution because the user ran it. Isolation is the host’s job. The one-click consent requirement is above. DNS rebinding against a local HTTP listener is in [3.15](3.15-transport-channel.md#localhost-exposure-and-dns-rebinding).

The child runs as the user. It can read what the user can read, including `~/.ssh` and cloud credential files, and it can open outbound connections, unless the host wrapped it.

**The environment comes along.** Unless the host builds a fresh environment, the child sees the variables the host already had, and the `env` block in config is added on top. A `GITHUB_TOKEN` exported in a shell profile is then visible to every local server. Put each server’s token in that server’s own config, and scrub the parent environment if the host allows it.

**Stdout is the protocol. Stderr is a log.** Servers are told to log on stderr because stdout is reserved for MCP messages. ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)) A server that prints tokens or tool arguments to stderr has written them into the host’s log. Redact stderr, and do not ship it raw to a shared telemetry pipeline.

The decisions that matter are the ones made before launch.

| Decision | Baseline | Stronger |
| --- | --- | --- |
| Does it need to be local? | If the server only calls a remote API, use the remote endpoint. | Run API wrappers in a central, logged environment. |
| Where did it come from? | You can name the publisher and you pinned a version. | Signature or build attestation at launch, plus an SBOM. |
| What can it see? | One project directory, read-only when the job is reading. | That directory is the only mount. Home, SSH, and cloud config are not in the container. |
| What can it call? | You know the expected destinations. | No network for local-only servers. An egress allowlist for the rest. |
| How does it get secrets? | Its own narrow token. | Short-lived credentials issued at start and dropped when the server is removed. |

Stdio does not care that the other end is `docker run -i`. Mount the project directory and nothing else. A container is not a perfect boundary. It does remove the common failures: the process read `~/.aws`, and the process called home.

A local server that listens on HTTP is a different problem from stdio. Stdio is reachable by the parent client. Loopback HTTP is reachable by other processes and, through the browser, by websites. Binding to `127.0.0.1` does not stop DNS rebinding. If a host must use local HTTP, require a token the website does not have, check `Host` and `Origin`, prefer a Unix socket, and do not bind `0.0.0.0`. A local proxy that accepts HTTP and then spawns stdio servers is a privilege elevator. Keep that proxy off the browser origin. ([Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices))

* [ ] Every configured server is still needed, and you can name who published it.
* [ ] API-only servers are remote, rather than a stdio process on the laptop.
* [ ] Third-party servers start with a scrubbed environment and a per-server token.
* [ ] Third-party servers are jailed to the project directory.
* [ ] Local-only servers have network disabled.
* [ ] One-click install shows the full command and refuses to continue without an explicit yes.
* [ ] Local HTTP listeners are authenticated, origin-checked, and absent from `0.0.0.0`.

### Developer workstations

An IDE host sits next to source code, SSH keys, Git credentials, package tokens, cloud credentials, local database dumps, and unpublished fixes. The exposure is the workstation, not a special MCP message type.

| Risk area | What can be exposed or abused |
| --- | --- |
| Source code | Proprietary code, unreleased products, security fixes, customer-specific logic. |
| Environment and Git credentials | API keys, cloud tokens, SSH keys, commit signing keys. |
| Local filesystem | `.env`, shell history, browser profiles, password-manager exports. |
| Terminal and dependency workflows | Package installs, lockfile tampering, curl-to-shell patterns. |
| Build and deploy tools | Accidental production deployment, infrastructure changes. |
| Logs and test data | Customer records, tokens in logs, internal endpoints. |

Command patterns the approval UI should flag, and the detection queries for them, are in [3.12](3.12-logging-detection.md#dangerous-command-detection). Secret paths are in [3.17](3.17-secrets-credentials.md).

| Control | Description |
| --- | --- |
| Workspace trust | Restrict MCP when the folder is untrusted. Modes are in [3.4](3.04-authorization-permission.md#workspace-trust). |
| Read-only by default | Allow search before write, terminal, Git push, or network. |
| Secret denylist | Block `.env`, private keys, and cloud credentials unless explicitly approved. |
| Git action separation | Treat `git status` differently from `git push`, branch deletion, or remote changes. |
| Agent-visible context limits | Do not automatically include the whole repository, shell history, or dependency tree. |

* [ ] MCP is restricted for untrusted workspaces.
* [ ] The client distinguishes read-only search from modification.
* [ ] `.env`, private keys, and SSH files are protected.
* [ ] Terminal commands are shown before execution.
* [ ] Git write operations are approved separately.
* [ ] External network calls are visible.
* [ ] Local tokens are short-lived and scoped.
* [ ] Logs do not capture secrets in prompts, tool outputs, or traces.

### MCPSTG-CONF-01 — Test MCP Server Configuration

<a id="mcpstg-conf-01"></a>

#### Summary

This test evaluates **test mcp server configuration** in MCP deployments. It focuses on deployment hardening, debug surfaces, and unsafe defaults. Failures often appear only when hosts, servers, tools, and upstream APIs are composed—single-component review is not enough.

#### Scenario

- **MCP host/client:** `<TEST_USER>` on a lab workstation with an MCP host config block (see **Example snippets**).
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` under `<TEST_WORKSPACE>`.
- **Tools/resources:** `<TEST_TOOL_NAME>`, `<TEST_RESOURCE>` (synthetic lab fixtures only).
- **Trust boundary:** host ↔ MCP server ↔ OS ↔ upstream APIs.
- **Attacker position:** malicious prompt, compromised server package, or abusive automation (lab-safe only).
- **Potential impact:** confidentiality, integrity, availability, or cost abuse depending on control gaps.

#### Test Objectives

- Confirm insecure behavior is absent or mitigated for **test mcp server configuration**.
- Identify missing controls (authorization, validation, egress policy, logging, rate limits).
- Document **secure** behavior under the same lab inputs.

#### Preconditions

- Authorized lab environment and written scope.
- Access to host configuration, MCP server configuration, and (if applicable) gateway policy.
- Test principal `<TEST_USER>`; secondary account if testing cross-user issues.
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review documentation, tool metadata, permission manifests, and architecture diagrams for gaps related to test mcp server configuration.

##### 2. Configuration Review

Inspect host MCP config, server env vars, transport settings, and gateway rules (redact secrets in evidence).

##### 3. Runtime Testing

1. Connect the lab host to `<AUTHORIZED_LAB_SERVER>` using the snippet in **Example snippets**.
2. Capture baseline `tools/list` (and `resources/list` if applicable).
3. Execute bounded runtime checks with synthetic arguments only.
4. Record host, server, and gateway responses plus redacted logs.

##### 4. Abuse Case Testing

Attempt bounded mutations: alternate principals, repeated calls, parameter edge cases, or sequencing—**no** destructive payloads or third-party targets.

##### 5. Log and Detection Review

Confirm logs include tool name, principal, decision, outcome, and correlation IDs without leaking secrets.

#### Example snippets

Lab host configuration (redact secrets before sharing evidence):

```json

      "command": "node",

        "WORKSPACE_ROOT": "<TEST_WORKSPACE>"
      }

  }
}
```

Invoke a tool with synthetic arguments:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
```

Use synthetic placeholders only. Replace `<TEST_*>` values with [Safe lab fixtures](test-case-format.md#safe-lab-fixtures) fixtures.

### MCPSTG-CONF-02 — Test Insecure Local Server Exposure

<a id="mcpstg-conf-02"></a>

#### Summary

“Local” MCP servers are often started on **localhost** with the assumption that only the trusted host process can connect. Exposure happens when servers bind to **all interfaces**, when **Unix domain sockets** have loose permissions, when **debug bridges** (for example HTTP-to-stdio proxies) are left enabled, or when **WSL / VM port forwarding** unintentionally publishes a port to the LAN. The impact equals remote access to powerful tools with **host user privileges**.

#### Scenario

- Developer runs MCP server with `--host 0.0.0.0` “so the container can reach it.”
- Corporate Wi‑Fi allows device-to-device traffic; attacker on same subnet scans for open MCP ports.
- **Potential impact:** Same as `MCPSTG-AUTHN-01` but framed as configuration error rather than missing auth middleware.

#### Test Objectives

- Verify effective **listen address** and **socket permissions** on all launch paths (CLI, IDE, CI).
- Verify **discovery** mechanisms (Bonjour, mDNS, IDE auto-expose) do not widen visibility unintentionally.
- Verify any HTTP bridge requires **loopback-only** binding or auth.

#### Preconditions

- Lab machine with permission to inspect listening ports (`ss`, `lsof`).
- Container and bare-metal variants if your users run both.

#### How to Test

##### 1. Manual Review

Read scripts, README quickstarts, and IDE default configs for bind flags.

##### 2. Configuration Review

- Check systemd unit files, Docker `compose` port mappings, Kubernetes `hostPort`.
- Inspect Unix socket path mode bits (`0777` vs `0600`).

##### 3. Runtime Testing

1. Start the MCP server the same way developers do.
2. From **another lab host** on the same network segment, attempt TCP connect to the MCP port—expect **refuse/timeout** for localhost-only designs.
3. For stdio, confirm no secondary listener exists unless explicitly configured.

##### 4. Abuse Case Testing

- IPv6 `::` dual-stack exposure when IPv4 is bound to loopback only—verify both families.

##### 5. Log and Detection Review

**Detection:** host EDR or firewall logs unexpected inbound to MCP ports; container image lint rules flag `EXPOSE` with `0.0.0.0` patterns.

#### Test Data / Example Payloads

Use `nc -vz <lab-ip> <port>` only against assets you own.

#### Expected Results

- **Secure:** localhost or authenticated mesh only; tight socket permissions; bridges off by default.
- **Insecure:** LAN-reachable MCP with host-user power; world-writable socket path.
- **Evidence:** `ss -ltnp` output, compose file snippets, photo-redacted IDE settings.

#### Remediation

- Default bind to `127.0.0.1`; require explicit env var to widen.
- Use `0600` sockets in user-private runtime dir; document WSL port-forward risks.
- Add CI checks that fail on dangerous defaults (`MCPSTG-GOV-03`).
