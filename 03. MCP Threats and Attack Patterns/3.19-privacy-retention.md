# 3.19 Privacy, Data Minimization, and Retention (`PRVC`)

[← Chapter 3 overview](<3. MCP Threats and Attack Patterns.md>) · [Test case format](test-case-format.md)

## Overview

Privacy tests verify **PII handling**, log retention, downstream copying of transcripts, and tenant/customer boundary labeling in context passed to models.

## Why this category matters

MCP blurs lines between chat, tool output, and resource content—each may contain PII subject to regulation and customer contracts.

## Scope

PII in resources/outputs, retention policies, cross-tenant labels, minimization before model calls.

## When to prioritize

Mandatory for **multi-tenant SaaS** and regulated data classes (health, finance, HR).

## Related categories

[CTX](3.08-context-memory.md), [OUTV](3.11-output-handling.md), [GOV](3.14-enterprise-governance.md), [LOG](3.12-logging-detection.md)

## Common test chains

PRVC-01 + RSRC-01; PRVC-03 + CTX-04 + AUTHZ-03.

## Threats and attack patterns

Privacy cases below are published disclosures of personal data through MCP tools: chat history, contacts, private repository contents, and email. Retention is included where the same write-up says the data remains after the package or the session is gone.

### WhatsApp history and contacts

Invariant Labs, 7 April 2025, tested Cursor connected to a `whatsapp-mcp` server. In the first experiment a second, attacker-controlled MCP server was also connected. They report that the agent exfiltrated WhatsApp chat history through WhatsApp’s own send tool, and that the malicious server did not have to be invoked. An update on 9 April adds a second experiment: the attacker only sends a WhatsApp message, that message appears in `list_chats` output, and they report leakage of the user’s contacts. They describe this as bypassing the value of WhatsApp’s own encryption, because the agent on the already-decrypted endpoint performed the read and the send.

> “Our WhatsApp MCP attack demonstrates how an untrusted MCP server can exfiltrate data from an agentic system that is also connected to a trusted WhatsApp MCP instance, side-stepping WhatsApp's encryption and security measures.”
>
> — Invariant Labs, [WhatsApp MCP Exploited](https://invariantlabs.ai/blog/whatsapp-mcp-exploited) (7 April 2025)

The 9 April update’s wording for the smaller setup: “a simple injected message is enough to hijack the agent into leaking the user's list of contacts.”

**Tests:** `MCPSTG-PRVC-01`. The data class is message content and contact identifiers, not only “files.” A tenant boundary does not exist inside one person’s WhatsApp account; the boundary that failed is between untrusted message text and the send tool. Cross-user handles are a different test, `MCPSTG-PRVC-03` and `MCPSTG-AUTHZ-03`.

### Email contents, including other people’s data

Snyk’s 25 September 2025 alert on npm package `postmark-mcp` says versions from about `1.0.16` added a BCC so that messages the agent sent were copied to an external domain. They list password resets, invoices, customer communications, and internal memos as the kind of data MCP mail tools handle, and they list customer PII and regulated data as impact if those were in the messages. They also write that installed copies keep sending after the package disappears from npm, until someone uninstalls them and changes the host configuration.

> “Data at risk: Any email content sent through the MCP server (including attachments and headers), potentially including secrets, tokens, customer PII, and regulated data that may have been present in such emails.”
>
> — Snyk, [Malicious MCP Server on npm postmark-mcp Harvests Emails](https://snyk.io/blog/malicious-mcp-server-on-npm-postmark-mcp-harvests-emails/)

**Tests:** `MCPSTG-PRVC-01`, `MCPSTG-PRVC-02`. Retention evidence is an installed server or a log pipeline that still holds message bodies after the registry yank and after the stated log lifetime. The package facts are in [3.13](3.13-supply-chain.md).

### Private repository data published on a public pull request

Invariant’s GitHub MCP write-up says private repository data was pulled into the agent’s context and then written into a pull request on a public repository, where the attacker and anyone else could read it. The Vulnerable MCP Project dates that post 26 May 2025 ([github-mcp-exploit](https://vulnerablemcp.info/vuln/github-mcp-exploit.html)). Willison, 16 June 2025, uses the case to argue that private data plus untrusted issue text plus an external write is sufficient for theft ([The lethal trifecta](https://simonwillison.net/2025/jun/16/the-lethal-trifecta/)).

The privacy consequence is retention outside the original repository: the public pull request is a copy the data owner may not find by searching the private repo. **Tests:** `MCPSTG-PRVC-01`, `MCPSTG-PRVC-02`. Customer or employee data inside a private repository is still personal data when an agent copies it to a public pull request.

### One session’s context used for another user’s state

The MCP security document (28 July 2026) describes state-handle hijacking: a cart id or workflow id returned in a tool result is later accepted as a tool argument. If the server does not bind that handle to the user in the verified token, a second principal who presents the handle reads or changes the first user’s state. The document says MCP at that spec revision is stateless, and it points to session-id hijacking guidance for protocol versions through `2025-11-25`.

> “State handle hijacking is an attack vector where an unauthorized party obtains or guesses such a handle and uses it to access or modify another user’s state.”
>
> — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices), State Handle Hijacking

**Tests:** `MCPSTG-PRVC-03`. The control is the server refusing the handle when the verified token is a different user. Context confusion is `MCPSTG-CTX-04`.

### Sampling as a privacy channel

The sampling write-up, including the example, impact, and host controls, is in [3.8](3.08-context-memory.md#sampling-abuse). The privacy failure is the direction of the call: `sampling/createMessage` returns the completion to the server, so conversation contents, other servers’ tool results, and any secret the model can see can leave with it. A host that auto-approves sampling, honors `includeContext: allServers`, or hides the sampling prompt from the transcript has copied context to a server that was not supposed to receive it.

**Tests:** `MCPSTG-PRVC-01`, `MCPSTG-CTX-03`.

### MCPSTG-PRVC-01 — Test PII in Resources and Tool Outputs



#### Summary

This test evaluates **test pii in resources and tool outputs** in MCP deployments. It focuses on PII minimization, retention, and tenant boundaries. Failures often appear only when hosts, servers, tools, and upstream APIs are composed—single-component review is not enough.

#### Scenario

- **MCP host/client:** `<TEST_USER>` on a lab workstation with an MCP host config block (see **Example snippets**).
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` under `<TEST_WORKSPACE>`.
- **Tools/resources:** `<TEST_TOOL_NAME>`, `<TEST_RESOURCE>` (synthetic lab fixtures only).
- **Trust boundary:** host ↔ MCP server ↔ OS ↔ upstream APIs.
- **Attacker position:** malicious prompt, compromised server package, or abusive automation (lab-safe only).
- **Potential impact:** confidentiality, integrity, availability, or cost abuse depending on control gaps.

#### Test Objectives

- Confirm insecure behavior is absent or mitigated for **test pii in resources and tool outputs**.
- Identify missing controls (authorization, validation, egress policy, logging, rate limits).
- Document **secure** behavior under the same lab inputs.

#### Preconditions

- Authorized lab environment and written scope.
- Access to host configuration, MCP server configuration, and (if applicable) gateway policy.
- Test principal `<TEST_USER>`; secondary account if testing cross-user issues.
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review documentation, tool metadata, permission manifests, and architecture diagrams for gaps related to test pii in resources and tool outputs.

##### 2. Configuration Review

Inspect host MCP config, server env vars, transport settings, and gateway rules (redact secrets in evidence).

##### 3. Runtime Testing

1. Connect the lab host to `<AUTHORIZED_LAB_SERVER>` using the snippet in **Example snippets**.
2. Capture baseline `tools/list` (and `resources/list` if applicable).
3. Execute bounded runtime checks with synthetic arguments only.
4. Record host, server, and gateway responses plus redacted logs.

##### 4. Abuse Case Testing

Attempt bounded mutations: alternate principals, repeated calls, parameter edge cases, or sequencing—**no** destructive payloads or third-party targets.

##### 5. Log and Detection Review

Confirm logs include tool name, principal, decision, outcome, and correlation IDs without leaking secrets.

#### Example snippets

Lab host configuration (redact secrets before sharing evidence):

```json
{
  "mcpServers": {
    "<AUTHORIZED_LAB_SERVER>": {
      "command": "node",
      "args": ["<TEST_WORKSPACE>/servers/lab-server/index.js"],
      "env": {
        "WORKSPACE_ROOT": "<TEST_WORKSPACE>"
      }
    }
  }
}
```

List and read resources:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "resources/list"
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "resources/read",
  "params": {
    "uri": "<TEST_RESOURCE>"
  }
}
```

Invoke a tool with synthetic arguments:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "query": "benign-lab-string-123",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Safe lab fixtures](test-case-format.md#safe-lab-fixtures) fixtures.

#### Expected Results

- **Secure:** policy blocks or contains abuse; stable deny/alert reason codes; limits and approvals enforced.
- **Insecure:** missing controls allow the abuse described in the summary; sensitive effects occur without detection.
- **Evidence:** redacted logs, config excerpts, snippet request/response pairs, policy screenshots.

#### Remediation

Apply least privilege, strong defaults, human approval for high-risk tools, input/output controls, gateway egress rules, rate limits, idempotency for writes, and secret hygiene.

#### Tools

MCP client utilities, HTTP/TLS proxies, structured log search, dependency scanners, and policy-as-code test harnesses (see [Testing tools](test-case-format.md#testing-tools)).

#### References

- Model Context Protocol documentation (cite version tested).
- OWASP LLM Top 10, OWASP API Security Top 10, OWASP ASVS where applicable.
- CWE and MITRE ATLAS where mappings are credible.

- [OWASP LLM Top 10](https://owasp.org/www-project-top-10-for-large-language-model-applications/): [LLM02 Sensitive Information Disclosure](https://genai.owasp.org/llmrisk/llm02/), [LLM06 Excessive Agency](https://genai.owasp.org/llmrisk/llm06/)

- Testing type: Manual
