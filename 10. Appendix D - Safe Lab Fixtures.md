# Appendix D: Safe Lab Fixtures

How to build the synthetic environment the tests in [Chapter 3](<03. MCP Threats and Attack Patterns/3. MCP Threats and Attack Patterns.md>) assume, and which placeholders to use when writing results up.

Every test in this guide is written for an **authorized lab**. No test step, payload or finding should name a real organization, customer, colleague, hostname or credential.

## Placeholders

Replace these tokens in examples and in public write-ups. An authorized internal report may also name the specific assets covered by the written scope.

| Placeholder | Use it for |
| --- | --- |
| `<TEST_USER>` | The lab principal running the client or host. Use a dedicated account, never a personal or production identity. |
| `<TEST_WORKSPACE>` | The lab workspace directory that the MCP server is allowed to read or write. |
| `<AUTHORIZED_LAB_SERVER>` | The MCP server under test. The name must make clear that it is lab-authorized. |
| `<TEST_TOOL_NAME>` | The tool being invoked on that server. |
| `<TEST_RESOURCE>` | The resource (file, record, document) the server exposes. |
| `<LAB_TOKEN>` | A synthetic credential. Never a real token, even a short-lived one. |
| `<LAB_MCP_HOST>` | The lab hostname of the HTTP MCP endpoint under test. |
| `<LAB_VALID_ACCESS_TOKEN>` | A currently valid synthetic access token for the positive control. |
| `<LAB_EXPIRY_ACCESS_TOKEN>` | A synthetic access token issued so the expiry case can observe it after its validity period. |
| `<LAB_REVOCATION_ACCESS_TOKEN>` | A separate synthetic access token reserved for the revocation case. It must still be unexpired when revocation is tested. |
| `<LAB_CASE_ACCESS_TOKEN>` | Whichever of the three access tokens the current step selects. Record an alias, not the token value. |
| `<TEST_USER_B>` | A second lab principal, for tests that compare what two clients were served. |
| `<LAB_PUBLISHER_IDENTITY>` | The lab signing identity a client expects for `<AUTHORIZED_LAB_SERVER>`'s manifest revisions. |
| `<LAB_OTHER_IDENTITY>` | A second lab signing identity that the client must not accept for that server. |
| `<LAB_TLOG>` | A lab transparency-log instance you operate. Never a public log: entries there are permanent. |

`<TEST_*>` in prose means "any placeholder from this table".

## Minimum lab layout

The example snippets in the chapter assume a workspace along these lines. Adapt the paths; keep the separation.

```text
<TEST_WORKSPACE>/
  servers/
    lab-server/          # the authorized MCP server under test
  current-repository-read-only/
  secrets/               # FAKE secrets only, clearly marked as such
    lab-token.txt
  data/
    <TEST_RESOURCE>      # synthetic records, documents, tickets
  logs/                  # host, server and gateway logs for the test window
```

A matching host configuration block (placeholders only):

```json
{
  "mcpServers": {
    "<AUTHORIZED_LAB_SERVER>": {
      "command": "node",
      "args": ["<TEST_WORKSPACE>/servers/lab-server/index.js"],
      "env": {
        "WORKSPACE_ROOT": "<TEST_WORKSPACE>"
      }
    }
  }
}
```

## Rules for fixtures

- **Synthetic data only.** Generate records, documents, tickets and messages. Do not copy a production dataset and call it a lab fixture.
- **Fake secrets are labelled.** Files under `secrets/` must be obviously synthetic (for example a value prefixed `LAB-`) so an accidental paste into a report is harmless.
- **One trust boundary per fixture.** Keep the client, the server, the downstream API stub and the gateway as separate components, so a test can show which one failed.
- **Reset between tests.** A fixture that still contains state from the previous test is the most common cause of a false positive.
- **No live third parties.** Point egress tests at your own stub endpoints. Do not use a real customer, a public API you do not own, or another team's service.
- **Lab network.** Where a test distinguishes local from remote transports, use lab addresses and lab DNS names only.
- **Destructive tests** (delete, install, write, approval bypass, egress) run against a disposable copy of the workspace, with the restore step written down before you start.

Use the [red team finding template](<03. MCP Threats and Attack Patterns/test-case-format.md#mcp-red-team-finding-template>) and the review status values in [Appendix C](<09. Appendix C - Security Review.md>). Redact secrets, references to internal systems, and any data that is not synthetic.
